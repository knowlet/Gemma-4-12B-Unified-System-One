# GX10 四核心 CPU：清理後逾時檢查與啟動修正

這一階段修正兩個會影響真實執行的問題：Decision3 短測必須等證據寫入、計時器與清理都完成後才可回報成功；文字輔助模型的執行環境盤點則補上已驗證的本機服務連線位置。新增程式已經過來源審查，尚無新的完整 Decision3 跑分或瀏覽器成功率。

## 實際執行發現

2026-10-23 13:04 UTC，原始閒置檢查通過，可用記憶體為 28,704,243,712 bytes，因此啟動一次 2 GiB、四核心的執行環境盤點。子程序在 0.1387 秒失敗，整個外層指令為 1.7453 秒：原本刻意清除的環境沒有使用者服務匯流排位置，使原始唯讀狀態查詢無法連線。失敗發生在原生檔案雜湊與 runtime 匯入之前，未載入模型、產生文字或執行 HTTP helper。原始清理紀錄確認所選程序已結束，兩次掃描為空，單元與 cgroup 均已不存在。

獨立的唯讀對照確認：相同狀態查詢在乾淨環境失敗，只加入經同一使用者、私有目錄與 socket 身分驗證的兩個本機連線變數後成功。修正放在獨立啟動層，保留原本 owner、邊界監督、觀察器及模型程式。實際執行仍須重新通過原始門檻；前次失敗不會升格為成功。

父程序的逾時監督另有環境差異：模型使用的 Python 缺少必要的 pidfd 系統介面，系統 Python 則具備。文字 helper 的監督父程序指定使用已驗證的系統 Python；模型子程序仍使用原本的模型環境。這不是模型品質或速度的結果。

## 保留完整限制的較小 Decision3 設定

新增 2 GiB 長時間設定沿用 CPU 16–19、400% 配額、swap 0 與原始主機保留額 26,119,172,916 bytes；啟動仍須至少 28,266,656,564 bytes，且 ComfyUI 閒置。完整兩套評測仍保留原題順序、選項、判分、16,384 token 上限、1,479 次請求，以及 180 秒單次、10,000 秒整批、10,800 秒外層限制。

原生 batch4 短測的成功判斷已修正：單次 20 秒與整批 120 秒都包含各自計時器清理後的檢查，整批也涵蓋最後證據寫入。清理或寫入失敗不能被成功回傳遮蓋，主要錯誤亦會保留。舊 3 GiB 短測的實測數字仍屬歷史觀測，不能替代新 2 GiB 設定的資格證據。Edge 是這個設定的測試目標；Lite 先前的記憶體峰值超過 2 GiB，未宣稱適用同一上限。

2026-10-23 13:31 UTC 的新啟動檢查仍顯示 ComfyUI 執行中，可用記憶體為 25,124,179,968 bytes，低於原始保留額；這次沒有建立新的模型工作。未停止 ComfyUI，也未更動其佇列或快取。

## 真正 HTTP 的準備與驗證範圍

另已準備一次真正 loopback HTTP 的文字 helper 測試，使用原始同步 client、25 秒與重試規則，並保留服務端完整請求 20 秒限制。仍須先完成執行環境盤點與真正模型／ASGI 短測，再選定 HTTP 指令並驗證；目前沒有實際 HTTP 或瀏覽器資格。

本輪有關驗證分別為：2 GiB 長時間 owner 37 個測試、原生 Decision3 短測 20 個、本機啟動層 15 個、完整評測候選 20 個，以及 HTTP 候選 36 個。這些是有界的 stdlib 假物件與來源檢查，各設定包含沿用測試；不是互不重複的模型實測，也不是品質分數。相關 Ruff、格式、AST 與預設不載入模型檢查通過，凍結來源及選定指令另經獨立審查。
