# GX10 四核心 CPU：較低記憶體設定與請求預算

這一階段完成 2 GiB 四核心執行環境盤點與真正小型 helper 測試的程式準備，保留原本主機保留額、模型輸入及時間限制。尚未完成新的模型載入、生成、HTTP 或完整 Decision3 評測。

2026-10-23 12:44:58 UTC 的啟動前檢查顯示 ComfyUI 正在工作（1 個執行中、0 個等待），可用記憶體為 25,015,144,448 bytes，低於原本保留額 26,119,172,916 bytes，也低於保留額加完整 2 GiB 的啟動門檻 28,266,656,564 bytes。這次沒有建立新的執行單元或載入模型，ComfyUI、快取及佇列都未更動。原先單元的兩次原始方法檢查皆為空，單元與 cgroup 也已不存在；這不會改寫先前中止紀錄中的失敗或資格欄位。

## 保留原始測試條件

新設定使用現有 owner03 的 CPU 16–19、400% 配額、2 GiB 上限、swap 0，主機保留額維持不變。盤點仍為 600 秒、兩次串流驗證同一組 9 個原生檔案，並確認 13 個執行來源與 5 個模組；不載入模型。helper 候選仍使用同一個原生 Qwen 0.5B BF16、8,192 token 上限、128 個新 token、真正 EOS、嚴格 JSON，以及獨立父程序的單次請求監督。超過長度會拒絕，不會截斷。

原始瀏覽器限制已重新核對：每題最多 **16 次決策**；**20 秒適用於每次完整 prediction/helper 請求**，不是整題或整批瀏覽器測試。helper 的 20 秒包括排隊、請求 body、生成、證據保留與 ASGI 發布；冷載入及 client 收齊時間另量。上游 client 原有 25 秒及重試規則不改。原始請求的 `max_tokens=1024` 與 helper 原定的原生生成 128 token 上限是不同層次的限制，兩者均保留。新的來源核查文件釐清先前紀錄中「whole20」的範圍，歷史凍結檔案不改寫。

原有 owner03 的 7,200 秒上限不足以保留完整評測原定的 10,000 秒預算，因此不能直接用它替換完整 Decision3 評測設定。較低記憶體的長時間評測需要獨立設定與審查；不得縮短評測預算、題目、上下文或原始判分條件。

## 驗證與下一步

2 GiB 盤點候選通過 13 個 stdlib 假物件測試，helper 候選通過 25 個；相關 Ruff、格式、AST 與預設不執行模型的檢查通過。新增測試確認相鄰錯誤上限、混用 owner、少保留任何一部分完整 2 GiB 都會被拒絕。這些檢查及來源審查不等於實際模型或 HTTP 成功。

待原始閒置與完整記憶體門檻通過後，先執行盤點並確認關閉，再測真正 NN/ASGI 的輸出、EOS、時間及記憶體。真正 loopback HTTP 與多次請求仍需各自驗證；所有比較模型必須共用同一個 helper。完整兩套 JevBench、相同真實瀏覽器場景及競爭模型比較仍是未完成工作。
