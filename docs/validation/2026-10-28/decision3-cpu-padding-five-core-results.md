# Decision3 五核心：合成長輸入分組實測

在 GX10 以 Decision3 Edge 的 CPU publisher 路徑執行一組自造四題文字輸入，實際 token 長度依序為 **3118／4197／4578／3126**，共 **15019**。每種模式先 warmup 一次，再交錯測量四輪；下表為完整請求時間，候選模式另包含快照及輸出檢查的開銷。p95 以 nearest-rank 計算；每模式只有四個觀測值，因此 p95 就是最大值，不能視為穩健的尾延遲估計。

四輪逐對比較中，長度分組耗時為原生的 82.94%–83.99%，約快 16.0%–17.1%；四題的選擇及 token 計量均一致，但機率並非完全相同。原生 `system_one` 未暴露原始機率列，這裡比較的是完整格式化回應。原批次、原順序分組及長度分組分別為 18312、17550、15408 個 padding slots。**最快模式仍超過原本 20 秒期限**，不得視為通過瀏覽器期限或可直接預設啟用。

實驗使用五核心（CPU 15–19）、500% quota、8 GiB 上限及零 swap。監督紀錄有 1062 次主機取樣，ComfyUI running／pending 均為零，最低可用記憶體 116181610496 bytes，最長相鄰取樣間隔約 0.525 秒；取樣無法證明間隔內或全機資源獨占。工作單元記錄峰值 3444711424 bytes，結束後 cgroup 及 process group 均不存在；單元保留為 active/exited、MainPID 0、Result success、ExecMainStatus 0。

獨立 CPU 稽核核對了固定計畫、回應與收尾，首次執行時回報 19／19 個來源指紋相符及三個 gate-only 副本相符。那次逐檔檢查只保存在工具執行紀錄，沒有持久逐檔 receipt。實驗後開始的十核心開發已修改 worker 與 watcher，因此後來再次從工作樹檢查舊計畫時，這兩個來源已不再相符；不得將首次結果解讀為來源持續未變或目前工作樹仍全數相符。模型 runtime 的完整傳遞依賴、執行期間權重及全機負載未獨立驗證。
