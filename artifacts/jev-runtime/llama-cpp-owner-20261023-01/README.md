# Owned CPU command preparation

This source-only wrapper reuses the unchanged terminal boundary and Comfy observer. It defaults to dry output. Running requires an independently selected controller SHA, an explicit root-authored command-spec SHA, a fresh `actual-NN` directory, and an absent exact unit. No unit, compiler, converter, Torch, model payload, or observer HTTP was executed during preparation.

The selected unit has 2 GiB `MemoryMax`, zero swap, 30 or 7,200 seconds of runtime, one CPU of aggregate quota, initial main-thread affinity CPU 0, core limit zero, 512 descriptors, and a 256 MiB per-file size limit. The latter allows compiler objects and executables; it cannot accommodate a full model GGUF. The observed main-thread affinity does not establish a delegated cpuset or prevent later affinity changes by every descendant. Shared GPU memory is outside this CPU probe's resource claim.

Before launching, the original observer must report Comfy idle or confirmed absent, and host available memory must be at least `R + 2 GiB`, where `R = max(24 GiB, ceil(MemTotal / 5))`. The wrapper first publishes its PID/start/session/cgroup and exact interpreter identity, then waits for parent admission after original boundary and kernel/property verification. The same stdlib process runs the selected command sequence using `Popen` with no implicit shell. The original logical executable path is retained for virtual-environment behavior. Its resolved target must match an explicitly selected tool stat. A command whose literal executable starts with `{OUTPUT}/` may instead run an executable generated inside that fresh owned output; its current stat and any actual child executable observation are recorded. That exception provides no preselected byte hash or model qualification.

The parent samples the unchanged Comfy/host reserve gate and owned-unit resources about once per second while commands run. Initial and final observations are separate. Raw loop observations retain the first 63 plus the latest observation, 64 total. The scalar summary includes every successful executed postlaunch readiness/preexec/loop gate, including raw rows later discarded; it is not a continuous minimum. Failed gates keep their observation in primary error evidence. The 30/7,200-second kernel runtime limit remains independent of the earlier command deadline and sampling interval.

Each command's stdout and stderr are continuously drained. Each stream saves only its first 4 MiB, while a normally completed drain records the byte count and hash of all observed bytes. Interruption can leave bounded prefix files without final stream counts/hash. These are explicit partial logs, not complete build logs. Completed command records, nonzero status, and cleanup failures remain available. The actor holds for at most five seconds after publishing its exit record so the parent can stop the exact admitted invocation through the original boundary. Success requires an authenticated stop of the live wrapper before that hold deadline, two original absence scans, final source checks, and the final host gate. No foreign process or service is stopped.

The source pool consists of at most 64 small exact refs and selected executable stats. It does not establish a complete installed-toolchain or source-tree closure. The root build spec additionally checks the upstream Git diff before and after compilation; its CMake flags disable selected fetch/UI/GPU paths. Environment/offline flags are not a kernel network sandbox. Build artifacts, native logs, caches, and any future tensors stay local unless separately selected for publication.

`root-tiny-test-spec.json` selects the separately reviewed synthetic BF16 converter regressions. `root-cpu-build-spec.json` selects the pinned llama.cpp CPU configure/build and server version command. They have distinct runtime budgets and must use separate fresh outputs. This wrapper's preparation and any successful build do not qualify full conversion, 12B inference, GPU transfer, context 8192, 20-second service, N3, Q95, or benchmark quality. Full conversion requires a separately reviewed memory/file-size budget; the known largest BF16 embedding alone exceeds this build profile's file-size cap.
