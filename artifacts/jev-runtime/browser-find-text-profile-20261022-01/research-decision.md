# Separate find-text profile: source decision

This experiment addresses the reachability hypothesis in `docs/research/jev-long-page-navigation-followup.md`. It does not change the existing V7 baseline, tasks, judges, observation, sixteen-action limit, model weights, numerical computation, or recorded scores.

Browser Use's MIT implementation at commit `aa093a843da5edbf323c0b4145c9b6a0db3ecde8` offers a model-selected `find_text` tool, dispatching a scroll-to-text event. Its [tool](https://github.com/browser-use/browser-use/blob/aa093a843da5edbf323c0b4145c9b6a0db3ecde8/browser_use/tools/service.py) and [watchdog](https://github.com/browser-use/browser-use/blob/aa093a843da5edbf323c0b4145c9b6a0db3ecde8/browser_use/browser/watchdogs/default_action_watchdog.py) establish an existing general navigation capability. We independently implement literal text-node navigation with safe JSON arguments, typed failures, current-document freshness and no task-specific routing. No upstream implementation code is copied.

The actual pinned ultrafast source constructs one operation question and up to three target questions. The previous Edge audit's fifteen heads were the sum across requests, not a fixed browser tensor geometry. `FIND_TEXT` is a ninth operation criterion with a null target; it adds no response head. Decision3's original native255 readout and native probability argmax can represent it without changing geometry or skipping any submitted head. Original generated-action and native request parsers correctly refuse it because their current eight-operation whitelist is fixed.

The implementation will therefore return a separate Agent subclass and privately compiled source derivatives of the original generated-action parser, legal-action grammar, and native adapter. It will not alter original module globals or files. Only the operation whitelist/count and explicit profile identifiers change. All grammar token/action limits, DTO widths, numerical functions, original ordered questions and labels remain intact. A request that exceeds an unchanged bound is rejected without pruning.

The model chooses `FIND_TEXT`; the existing text helper then supplies a literal query through its unchanged `TEXT_VALUE` two-message JSON schema. Its `field` is explicitly a logical `browser_find_query` parameter, not a claimed observed form input. The helper sees only the actual user goal, current observed page and recent history. A query/search attempt consumes one of the existing sixteen actions, including not-found, stale or late outcomes. No click, typed input, task success or physical scroll is inferred from an attempted call. Typed result feedback reaches the next request through separately labelled profile state.

Search is a bounded single-document text-node scan. It excludes hidden/script/style/template content, accepts an offscreen rendered match, and requests instantaneous scroll only after a second same-document marker check. A stale document, no match, scan limit, helper failure or deadline is recorded explicitly. Source-only and fake-I/O tests cannot establish actual browser/CDP behavior or navigation quality.

The existing qualified S1/D3 owners, bootstrap descriptor, native wire-profile selection and Q95 policy qualification remain unchanged and do not admit this operation. A separately selected server/bootstrap and real browser validation are prerequisites for any model run or score claim. Reusing the existing Q95 text-helper schema establishes schema compatibility, not query quality or a new policy qualification. No new owner, service, model launch or success claim is part of this component.

Exact local source hashes are recorded in `source-pins.json`. The DevTools [Runtime.evaluate protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/js_protocol.json) documents evaluation and timeout behavior; host-side timing remains cooperative and cannot undo a navigation already requested.
