# CUDA context and tiny BF16 operator probe

Source prepared only. The preparer did not import Torch, execute CUDA/NVML, inspect a model header/payload, mmap weights or launch an actor/service. Only the reviewed root owner may run this separate GPU profile; the existing CPU/Q95 profiles are unchanged.

`fixture.py` is dry by default. Explicit execution uses the existing `--run --profile --selection --selection-sha256 --entry-sha256 --output` CLI with profile `gpu-context-probe-fixture-v1`, a fresh ordinary output, fixed `CUDA_VISIBLE_DEVICES=GPU-e3429caa-b057-cbe0-917d-d3b85b313be7` and parent-sealed `JEV_GPU_PROBE_DEADLINE_MONOTONIC`. One CPU thread and disabled TF/Flax are required. The owner controls its own CUDA cache directory. Generated driver-cache binaries remain local and must not be staged.

The ten immediately fsynced stages are: stdlib baseline; Torch import/pre-init; explicit lazy-init return; first explicit synchronize; fixed64MiB own allocator cap; two16×16 BF16 ones allocations/fill; fill synchronization; matmul/synchronization;512-byte CPU readback/exact oracle; own tensor deletion/GC/empty_cache. Each saves elapsed time, faults, process RSS/Anon/File, own cgroup current/peak/stat, host memory and permitted CUDA counters. A CUDA-metrics failure still saves the CPU stage evidence before propagating the error.

Before the first explicit synchronize, only the initialized flag and process/cgroup/host data are read: CUDA free/allocated/reserved are **unmeasured**, not invented zeroes. `init_call_seconds`, `init_sync_seconds`, metadata/metrics time, fill enqueue/sync, matmul enqueue/sync, readback and release are separate. The init-return stage is not a claim of complete physical context creation. Ones fill can execute before matmul; this is not a claim that matmul is the first kernel.

After synchronization, logical device0 must join the root-pinned physical UUID. Actual allocator backend and integrated-device property are recorded. The64MiB fraction limits only the process's PyTorch caching allocator; it does not bound context, driver, cuBLAS, UMA physical memory or total cgroup charges. Unknown/failing APIs cause failure without increasing the cap. Global CUDA free and host MemAvailable are distinct observations and are never added or treated as an owned-process delta.

The tiny oracle is independent of model weights: ones16×16 multiplied by ones16×16 must produce256 BF16 values exactly16, with the independently specified `0x4180` bit pattern. Only output hash/shape/dtype/exactness are saved. This proves a tiny fill/matmul/readback path, not model transfer, decoder numerical parity, accuracy or throughput.

Success retains initialized CUDA state (`CUDA.initialized_final=true`), all ten stages and exact oracle checks. Insufficient parent deadline writes a partial receipt and exits2 with completion flags false. Other failures exit1, preserving the primary error and cleanup evidence; pre-run refusals may have no output. Cleanup first attempts own synchronization, then clears tensors/GC/empty_cache even when synchronization fails. A blocked native call can hit the owner hard limit before a final receipt; earlier fsynced stages remain. `empty_cache` only releases unused own allocator cache; it does not destroy the context. Authenticated owner process/unit closure remains required.

`selection.json` retains the four-key schema, exact Torch2.13.0+cu130 version,11 small source/authority hashes and six native-library stat identities. This is not a complete native runtime closure. Preparation validation is17 pure-stdlib tests in0.097 seconds plus Ruff PASS; fake API tests do not establish CUDA success. No model/UMA capacity,12B,8192 context,20-second,N3/Q95 or benchmark qualification is claimed.
