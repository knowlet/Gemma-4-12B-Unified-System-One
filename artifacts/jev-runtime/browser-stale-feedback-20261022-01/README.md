# Repeated stale-page decisions: recorded evidence and CPU proof

Raw03 public6 attempt `heldout-public-003-000` made 16 policy calls but recorded only three executed action entries. Calls 5 through 15 sent **the same 16,021 original HTTP bytes**, SHA `8dc4610f10a04c852f51a4539a9d195fccb141efcdae53fbb3210a23b4407b39`, at consecutive HTTP sequence numbers 67 through 77. All eleven decoded decisions selected CLICK target 39. States 5 through 16 retained the same complete page and history. The eleven full HTTP response bodies differ because telemetry differs; only decoded answers are equal.

The source is the exact five upstream files selected by raw03, at upstream commit `1231850a0bf1a0c0341fe408ef1668dbbfdfac46`. The proof compiles the verified original Agent, model, question and Browser definitions directly from source bytes. Its private browser/network fixtures perform no real browser, model, daemon, service, unit, network or GPU work. The original `Agent.command("tick")` catches `StalePage`, clears the decision, sets ready and observes again. On a pre-input rejection, no execution history entry has been added; when the page also stays unchanged, the original `choose` builds exactly the same next request. The fixture demonstrates three repetitions. A changed-page control produces a different request. A post-input stale-observation control retains the executed action entry, as the original loop intends.

This supports a missing-failure-context mechanism. It does **not** identify the physical guard branch in the actual raw03 run: freshness mismatch, covered/changed target and interrupted observation can all produce the same exception class. Missing history alone does not prove that no physical input occurred. The run did not preserve a typed branch receipt, so that cause remains unproven.

A small successor can add one separate `state.last_attempt` field to the next policy request: typed outcome `stale_page`, attempted operation/target, recorded action-count delta, whether the observed fingerprint stayed equal, and consecutive count. Record these facts in the catch path before clearing the consumed decision. Keep actual action history, complete observed candidate inventory, DOM judges and browser safety checks unchanged. Count recorded actions explicitly because an exception can also happen after input. Do not infer a covered target, physical failure cause or unexecuted action from the exception class alone. The proof's schema illustration changes only this separate request field. It is not installed in upstream or the selected model adapter.

Four pure CPU tests passed under 256 MiB address space, 30 CPU seconds and 45 wall seconds; Ruff passed. `proof.py` additionally checks actual stored request/response hashes and exact decoded joins, then writes `proof-receipt.json` with counts and hash references only. No raw DOM, request content, answers or goal text is published here. This establishes request/loop behavior, not a measured improvement or a scenario-success claim. A new explicit observation profile still needs an actual controlled browser evaluation.

The V2 result is a separate completed evaluation: it changes both adapter and serialized observation format. This proof neither assigns the V2 improvement to stale handling nor alters those completed outputs.
