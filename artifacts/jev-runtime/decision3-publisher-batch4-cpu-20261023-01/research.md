# Fresh native batch-four CPU probe: Edge and Lite

This successor is source-only while the original Edge batch-one campaign stays active. No active outputs/processes/cgroups/managers, benchmark data/gold, tensor headers/payloads, large tokenizer bytes, runtime or model are read/executed. Existing frozen sources and active jobs remain unchanged. The preparation reuses previously reviewed publisher/runtime research and authenticated small source/configuration references, not batch-one scores, outputs or admission.

Before implementation, publisher `D3.from_pretrained`, `D3.__init__`, `run`, `probabilities`, `logits`, `respond` and `PromptEncoder.__call__` were read from the pinned local source. Edge revision `cab71e6ad3461b8086d51ddb572c656babd63b0b` and Lite `9c10703193afc7c7d28c88201c0364bfbbf58320` have the identical `d3_runtime.py` SHA `adf7f7aa085674b5682e492d8b2e3cc4f11c67b0d153515c742e907e9b550917`. `from_pretrained(batch_size=4)` still calls one constructor and one backbone loader. `run` takes each original request's ordered runnable keys in chunks of four, passes their original full sequences/counts to `probabilities`, and restores original answer order. It does not merge requests. The shipped `DEFAULT_BATCH_SIZE=8` constant is unchanged: four is an explicit supported API option in this distinct profile.

`logits` left-pads a batch to that batch's longest prompt, builds the original per-row masks, calls the same BF16 backbone/SDPA noncausal full-attention plus causal DeltaNet and original FP32 readout, and keeps the last prompt position. No prompt, option, temperature, context, pooling, math implementation or kernel availability function is changed. This preserves semantics, not bitwise batch-one equivalence: padding/batch dimensions can alter BF16 arithmetic or reduction choices. Padding also raises activation/workspace cost; four short rows cannot establish fit/latency for longer benchmark prompts, all 255 options, mixed media or a 16,384 context. Original reference CPU kernels remain required and actual bindings are inspected. There is no quantization or GPU shim.

The installed Torch `nn/modules/module.py:register_forward_pre_hook` source was read. Its documented hook signature returns `None` to leave inputs unchanged. The probe uses that ordinary observation hook on the first decoder layer, records only shape/dtype/device and explicitly returns `None`. Four independent developer synthetic choice questions retain their original order with differing prompt lengths. The request is repeated twice using one constructor, requiring exactly two genuine four-row first-layer forward observations and two fully validated native responses. No expected semantic answer/gold is a pass criterion. This proves actual grouping rather than inferring it from the batch-size flag alone. The hook never examines values, weights or modifies a kernel/forward input/output.
