# Native llama.cpp Decision API: source-only review

Pinned llama.cpp `184f6536024668e8908ab8c86033d56708e62b40` has a real `POST /v1/systemone` implementation, including `vllm-d3` and `pplx-decider` model types. This can provide a mature future Decision3 HTTP route. It does not make the current causal, 52-label Gemma S1 runner a Decision3 engine, and no build, model access, conversion, download, Torch import or server execution occurred in this review.

`tools/server/server.cpp:308` registers the route. `server-context.cpp:6481` rejects a model without native decision metadata with unsupported/501, parses the state/questions, creates decision tasks, waits for their results and returns:

```json
{"model":"actual-server-model","answers":{"q":{"type":"choice","choice":"first","probabilities":{"first":0.7,"second":0.3},"confidence":0.1187}},"usage":{"input_tokens":123,"output_tokens":0}}
```

Those numbers illustrate the schema only; they are not model results. Requests contain `state` and a nonempty named `questions` object. Each question has `type` (`choice`, `score`, `noul`), `instructions`, and `criteria`: an ordered option-to-description object for choice, 2..10 ordered level descriptions for score, or optional true/false descriptions for noul. D3 allows null state and omitted instructions, using its template default. Its non-strict parser accepts a nonempty choice object, including a singleton; the upper bound is the model's discovered labels. `common_json` preserves insertion order, and D3 does not enable the sorting path used by other specific models. The ordinary response preserves question IDs and candidate-key probabilities. Invalid inputs return 400, unsupported model/media routes 501; streaming is not supported.

| D3 behavior | Actual pinned implementation |
| --- | --- |
| Labels and 255-option limit | `server-decision.cpp:106` enumerates A..Z, then AA..ZZ, keeps single-token codes and stops at 255. Runtime token IDs must still be checked against the publisher's pinned 255 readout IDs; registration alone does not establish their equality. |
| Prompt and questions | `VllmD3Model` writes the publisher-specific named `systemone` template. `fill_task` builds each question's own prompt; D3 has one variant, is not joint, and is excluded from common-prefix sharing. One multi-question HTTP request therefore has separate decision tasks, rather than Gemma S1's single ordered multi-slot prompt. |
| Attention | Converter guard requires `noncausal_full_attention` and writes causal-attention false. Server forbids splitting a noncausal decision prompt, so the complete prompt must fit physical `--ubatch-size` as well as context. A 512 microbatch used for the Gemma smoke cannot qualify an 8192-token D3 request. The Qwen hybrid's full-attention layers become noncausal; its other native graph mechanisms are not replaced by a generic bidirectional transformer. |
| Pooling/readout | Converter requires `pooling="last"`. Server marks the last prompt token as output, then `send_decision` reads that token's full-vocabulary logits and selects the first N legal code IDs. The decision slot is released immediately, before sampling/generation. No autoregressive answer is fed back. |
| Probabilities | `format_answer` softmaxes legal scores with the stored type-specific temperature (one variant for D3). Choice is argmax; score is expected index plus legend; noul is the true probability. D3 confidence is normalized entropy. `usage.input_tokens` sums question prompt tokens and `output_tokens` is zero. This is algorithm evidence, not numerical parity or calibration evidence. |

The prior small-config audit at `llama-cpp-checkpoint-metadata-20261023-01/decision3-converter-metadata.json` found that all six already pinned Decision3 configs match `d3-code-readout-v1`, `d3`, `noncausal_full_attention`, `last`, with 255 unique readout IDs. Their converter detector selects `VllmD3Model`, inheriting `PplxDeciderModel`; generic Pplx detection deliberately excludes configs containing `format_id`. This establishes a registry/config path only. Completeness of each local snapshot, conversion, token/prompt/readout parity, native graph support and actual memory/time remain unmeasured.

No upstream CLI bypass for the dense generated head was found in the complete pinned converter argument surface or D3/Pplx generation code. `PplxDeciderModel.generate_extra_tensors` unconditionally loads `readout.safetensors`, creates `torch.zeros(vocab_size, readout_width, dtype=readout.dtype)`, assigns the 255 code rows and emits `lm_head.weight`. Existing configs use FP32 readout: even edge/lite creates 1,017,118,720 bytes; d3 creates 5,085,593,600 bytes. `--outtype` can change later stored precision, but does not remove that initial dense allocation; `--use-temp-file`, lazy writing and split-output flags do not change this function. `--vocab-only` would omit usable model weights, not provide a readout-capable shortcut. On the runtime side Qwen35 builds its ordinary full output matrix multiplication, and `send_decision` selects legal logits afterward. A sparse/selected-row readout route would be a new implementation and needs its own numeric qualification, rather than an undiscovered flag assumed here.

The existing Gemma4Unified converter writes neither a `<arch>.decision.type` marker nor a named `systemone` template. `common_get_decision_type` returns NONE without that marker, so plain released Gemma Q8 is not automatically accepted by this HTTP endpoint. The custom `tools/gguf/s1_gguf.cpp` remains the evidenced Gemma slot-scoring bridge: 52 legal letters, all answer slots retained in one causal sequence, one decision evaluation with possibly several physical decode calls. D3 has up to 255 codes, independent per-question prompts and whole-prompt noncausal full attention. Merely pointing that S1 executable at D3 is semantically incorrect.

Native typed decisions do not solve field-text generation. `server-common.cpp` advertises D3 and Pplx as `output_modalities:["decisions"]`, not a text-generating model. The original full-vocabulary generative Gemma weights can be a separately selected helper through the existing chat/completion API, but its field schema, stopping, EOS, 128-token/20-second budget and actual browser outputs need fresh evidence. No helper was implemented here. The model router does proxy `/v1/systemone` and chat completions, so one public server address may route D3 policy and Gemma helper requests to different models; that does not establish one shared model/context, one resident allocation or resource fit.

LoRA support is concrete but bounded: `--lora`, `--lora-scaled`, `/lora-adapters` and completion-request `lora` scales exist. The inspected `/v1/systemone` handler never calls `parse_lora_request` or populates per-task LoRA scales from its body, so per-decision adapter switching cannot be inferred from completion support. Its decision tasks use the server's loaded global adapter configuration. Applying a new compatible GGUF LoRA still needs conversion, identity, math and cache/lifetime validation; the current Gemma browser LoRA is not an adapter for the Qwen-based D3 models. A shared Gemma policy/helper model with distinct adapter states is a prospective integration, not an upstream feature proven by this endpoint.

The concrete next route is to retain the current separately scoped Gemma S1 smoke first, then verify an existing d3-edge snapshot by metadata/stat and prepare a fresh upstream Decision3 conversion/load plus bounded native server build. Compare exact rendered prompts, all 255 labels/readout identities and legal distributions to the pinned publisher path before any browser/JevBench score. Any native-server browser arm should keep the original harness transport journal, seed, task inventory and judges, use actual reported model identities, and explicitly select its real helper. It must retain the original gates and avoid inheriting N3/Q95 or earlier Metal quality claims.
