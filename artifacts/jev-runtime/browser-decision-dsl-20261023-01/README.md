This is an independently authored synthetic workflow source corpus for a possible future frozen-encoder/readout experiment. It contains no model features, predictions, training, browser execution or official benchmark evidence. It does not establish better real-browser behavior.

The fixed population is 168 branch snapshots from 21 workflow ancestors: 96 train states from four families and twelve ancestors, 24 development states from one family and three ancestors, and 48 sealed states from two families and six ancestors. These are eight counterfactual branches per ancestor, not a claim that an eight-step trajectory was executed. The family assignment precedes entity names, phrasings, branches, control orders and criterion permutations. Every descendant stays in its family's split.

The domains are appointment editing, staged document submission, inventory reservations, saved administrative filters, expense claims, course enrollment and equipment checkout. The seven workflow definitions have domain-specific facts, controls and explicit requirement orders, covering all six orderings of three requirements. The shared DSL language, original question instructions and standard protocol are common across splits; the sealed set tests new authored families within this language, not arbitrary unseen websites or a wholly unseen action grammar. Each family has three entity/phrasing ancestors and branches for partially completed requirements, a missing visible checkbox or final submit, lower/upper off-screen controls, transient processing, saved completion and permanent denial.

Goals specify the required order and explicitly permit skipping requirements already satisfied. That makes released next-action sets unambiguous without selecting a convenient first target. `solve()` also supports an authored parallel-details mode: all equally valid actions survive as a set. Labels give uniform probability to all valid offered positions and zero to the others. The original offered target heads remain present, but unused target heads receive no supervised answer. Saved completion requires visible receipt evidence matching every requirement. Pending submission permits WAIT; permanent lack of permission with no supported recovery permits BLOCKED. Unrelated controls remain as distractors.

The selected profile is the unchanged standard eight actions: CLICK, TYPE_TEXT, SELECT, SCROLL_DOWN, SCROLL_UP, WAIT, DONE and BLOCKED. Filling a field uses TYPE_TEXT and checking a checkbox uses CLICK. No FIND_TEXT action is introduced. A TYPE_TEXT label selects the existing operation/target only; it does not supply field text or replace the genuine shared text helper in any future browser run.

`request_builder.py` verifies the two pinned upstream source hashes, extracts exact `action_space`, `choose`, `NEXT_ACTION` and `TARGET` AST nodes, and stops at `choose`'s original `post_json` call. It does not import the original module or construct its HTTP client, and it does not fabricate a model response. Each case retains the resulting state, instructions, four original questions and all offered options. Every operation question offers all eight standard choices; every target head has four candidates. Only their declared order changes. Eight cyclic operation permutations are predeclared by ancestor ordinal; each ancestor places its eight labels once at each operation position. Target placements cycle through four predeclared positions. Static audit reports the full operation/label-position and target/label-position contingency tables, not a model confusion matrix.

`generate.py` defaults to a dry metadata message. Its only writing destination is this package's fresh `corpus` subdirectory; it refuses to overwrite an existing output. `corpus/authored-cases.jsonl` retains the full synthetic DSL states and semantic annotations for author/reviewer audit. Each split separately exports requests, labels and a summary. A label carries the exact request hash, actual criterion IDs, valid IDs/positions and soft targets. No features, logits, embeddings or native outputs are generated or accepted by these tools.

The captured request retains upstream's default `jev-latest` routing tag as source metadata. It is not a model binding for a future collector. Both request and label records additionally bind the exact native `{state, questions}` projection hash; a future independently reviewed owned collector must preserve and authenticate that projection rather than silently relabel or reshape questions to change the routing tag.

The operation head is first, while target-head row order follows the original `action_space` insertion order and therefore varies with the authored observed-control shuffle. The plan's four head names describe the schema, not a fixed row order. Future collection must associate every feature and label by the actual request's ordered question IDs and projection hash; it must never zip against a constant target-head list.

The sealed labels are procedural source holdouts, not cryptographically secret material. Generated raw requests, labels and full authoring states stay in the ignored local `corpus` directory; only source and aggregate identities/counts are in the review freeze. Future optimizer execution must select only the three train export files under `role-policy.json`; it must not receive authoring code, full authored cases, full manifest, development files or sealed files from which labels can be reconstructed. `check_role_selection()` rejects cross-split selections, unknown roles/ancestors, noncanonical paths and tainted derived artifacts. This is a pure root-side metadata check, not an OS sandbox or a loader. A separately reviewed owned loader and collector are still required to authenticate hashes, restrict actual file access, preserve taint, and reveal sealed evaluation only after the candidate is frozen. No optimizer, feature reader or reveal command is included here.

The checker itself imports the full authoring DSL, so it belongs only in the root metadata process. It must not be imported by a future train-only optimizer. The future optimizer needs separately selected math/loader source and authenticated train exports, not any Python module from this authoring package.

No existing canary fixture, official browser task, Jev task, gold answer, browser DOM, answer cache or model failure output was used to author these workflows. The two upstream files supply request construction and generic instructions only. The authored domains intentionally exclude the earlier diagnostic domains. Dataset semantics and split policy are fixed before any NN execution on this corpus. Future native features and model outputs must remain outside Git and must not be mixed into this source freeze.

Upstream construction and instructions are from the existing pinned Browser Use `jev_ultrafast` sources: model.py SHA `a85ada8458d23642c5c8a4095acf0565e6268f81dcda26f6308942b653e9c9f3` and questions.py SHA `66a7054b85040b949e1757311257ea0c5a843c635f9a40c99f6d15ad660fb422`. The existing upstream MIT notice is retained verbatim in `UPSTREAM-LICENSE`. No upstream task corpus is read or copied.

All source, corpus identity and validation claims must be read with the saved validation receipt and final freeze. Source tests check population/ancestry leakage, complete valid-action sets, actual option positions, wrong-target corruption, WAIT/DONE/BLOCKED semantics and role/taint refusal. They are not NN, HTTP or browser qualification.
