## Real parent authority and deadlines

`authority.py` accepts only a hash-bound private ticket containing the real parent, worker and unit-main PID/start/UID/cgroup, current boot, original nonce/invocation and the inherited authenticated socket channel. The parent independently verifies original unit properties on startup and request arm. Every authority call rechecks real process identities and requires an ordered authenticated parent reply. This is not an authority-shaped test object or a cooperative worker thread presented as an external watchdog. No per-token observer or full-host admission policy is added; original owner05 remains the independent R/swap/Comfy authority.

The parent tracks a 180-second whole smoke budget including snapshot preparation, loading, request, receipts and cleanup. It starts tracking the original 20-second request deadline at the first native ASGI checkpoint (which precedes the original arm), and refuses deadline replacement/extension, a second arm, or cancel/finish/disarm messages. The worker must receive actual parent authorization to continue. The parent polls at most 50ms while free to run and signals only its exact identity-bound child via pidfd on failure/expiry, before attempting failure evidence. The original owner still controls whole-unit cleanup if either process fails. PID identity, kernel/cgroup reads and scheduling may delay observation; no absolute hard real-time20-second guarantee is claimed. Future actual receipts must measure observed timing and original closure.

The original helper includes queue, retention/fsync and cooperative ASGI publication in its 20 seconds. The parent also keeps the same deadline active through worker receipt, child exit, parent receipt and cleanup. A late post-cleanup check or cleanup failure demotes the candidate receipt, clears qualification and retains the primary exception; failure evidence errors become notes and cannot replace the primary. Already queued transport bytes cannot be retracted, and this source does not claim otherwise.

## One smoke request and its limits

Only the future worker creates a fresh random opaque reference string. It submits one original-shape context through the actual frozen public factory and requires native generation to return that string as exact JSON. The string is an input and an assertion, never an alternate generator or a decoded/gold-derived shortcut. There is no task-name matching, benchmark task, gold, DOM fixture, replay or fallback field value in this package. Failed JSON, missing native EOS, timeout, wrong value or evidence failure cannot qualify the smoke.

The transport is **in-process ASGI**, with a declared loopback scope, bearer authentication and native request/response body handling. It is not an actual HTTP connection or listening endpoint. Real loopback serving and policy/browser integration remain later work. One smoke success would qualify one actual NN/ASGI request only; it would not qualify general helper quality, arbitrary browser completion, browser scores, full native DSO closure or hard20. The same fixed helper must be shared across all compared policies, preserving the existing tasks/judge/16steps/whole20/options.
